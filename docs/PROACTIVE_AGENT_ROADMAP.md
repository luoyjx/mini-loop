## 结论先行

主动个人助理需要六个部件：常驻运行的「自己的电脑」、应用集成、记忆、routine/触发器、审批闸、审计账本。mini-loop 的 Go 运行时已经具备其中最难补的治理部分：带风险分级的 `ToolGate`、权限模式、action journal、SQLite 状态、owner 记忆和 typed extension tool。缺的是「常驻 + 事件驱动 + 对外信道」这一层。

demo 已经用 Go 做了十二轮。D0 是一个只监听回环地址的守护进程，加一个模拟信道网页。D1 按拍板结果做了三件事：

- 邮件和日历挪进一个独立子进程里的模拟 MCP server；
- 新邮件改为轮询发现，批准后的发送经 MCP 执行并带幂等键；
- 守护进程可以用 launchd 常驻在本机 Mac 上。

D2 补上「把一件事跟到完成」：

- worker 可以建持久任务，并给自己约定检查时间。到点后，scheduler 叫醒同一 thread 的 worker；它核对进展，完成就关闭任务，没完成就约下一次。
- 同一 thread 上提案的结果（发出、被拒、发送失败）会把任务的检查提前。
- 每个任务都有兜底检查和检查次数预算，用完就转交给用户。
- 新增「日程临近」时间触发：会议开始前 15 分钟提醒一次。
- 不同 thread 的事件本来就并行处理（默认 4 个 worker）。页面现在会显示正在运行的 worker 数，测试也验证了并行和同 thread 串行。

D3 对照 DeepSeek 开源的 `dsh-superagent` 研究原型，把「尽量少占用人的注意力，人随时能接管」落到页面和调度上：

- 页面顶部只列需要你处理的事：待批准、发送失败、转交给你的任务、失败的触发器、连续失败 3 次的组件；每项直接带操作，没有待办时整块隐藏。
- 一个持久的暂停开关：照常收信，但不派工、不发信、不跑定时检查，重启后仍然有效。
- 你发的消息先领取，并且多留一个只给你用的 worker 槽位。
- 修了一个真实缺陷：agent 会话把模型调用失败当作最终文字返回，以前会被当成助理的回复发到信道。现在它算失败的回合；MCP 拒绝、4xx 和回合耗尽不再重试，其余退避重试。
- 数据目录加了独占锁，同一目录只能跑一个守护进程。

D4 把对照里剩下的两项建议都做了：

- 同一 thread 在 worker 忙时积压的事件，领取时合并成一回合，只汇报一次。聊天和其他触发器不混在一批里，routine 总是单独跑。
- worker 用结构化的 `report` 工具汇报：notify 发到信道，ask 向用户提一个问题，quiet 只写账本。`[QUIET]` 文字标记去掉了。问题出现在「需要你处理」里，用户的回答回到提问的 thread，由同一个 worker 接着处理。

对照的完整清单和后续取舍见第 2 节。

D5 做了路线里的 P5（主动性增强）：

- **准入分级**：已知联系人直接写给你，算明确请求，直接派工；已知联系人抄送你、或陌生人直接写给你，算推断候选；陌生人抄送你，只归档。联系人表预置 4 人，你批准发出的邮件会把收件人记成联系人。
- **分诊**：推断候选先过一次不带工具的模型调用，结论是 handle、observe 或 ignore。默认的观察模式下，分诊建议处理的也只记录在页面的「候选」里，由你交给 worker 或忽略；切到自动模式才直接派工。分诊失败一律只记录。
- **后台准备**：worker 用 `prepare_start` 开一个后台准备任务，在只有读工具的会话里提前收集材料，例如收到账单先和上月对比。结果作为 `job.done` 触发器回到原来的 thread，由那里的 worker 决定要不要告诉你。任务可以停止，重启后重新排队。
- **看门狗**：每次任务检查都记一份快照，scheduler 每轮用 agent 自带的卡住检测器判断。连续 3 次要核对的内容和进展都没变，就在「需要你处理」里提醒你。
- **验收**：300 条合成事件流用离线脚本模型跑完，共 112 个 worker 回合，安静率 0.54，p50 0.51 秒、p95 1.01 秒。

D6 做了路线里的 P6（长期记忆）：

- **链式召回**：只读的 `lookup` 工具按引用（`trigger-`、`task-`、`proposal-`、`question-`、`job-`、`thread:`、`session:`）读一条本地记录，返回摘要和下一跳的引用，worker 可以顺着追溯一件事，不用靠搜索。
- **夜间整理**：每晚 23:30 的 routine。worker 回合之前，守护进程把已发送邮件的收件人记成联系人（发件人不算），从日历算出会议时间窗，去掉内容重复的记忆，重建用户画像；然后 worker 读当天你在信道里说过的话，把其中的偏好用 `remember` 记下。
- **用户画像**：经理、常联系的人、会议时间、偏好四项，写进每个 worker 的提示，只当参考。
- **检索评估**：现有的词面检索能找到主题词和空格分开的关键词，找不到换了说法的问题。语义检索需要新依赖，要先审批，这轮没有加。

D7 是记忆检索三步里的第一步（2026-11-02 拍板：本地嵌入模型可以用，云端默认不开），不加任何依赖：

- **混合检索**：worker 用新的 `memory_search` 搜记忆。三路分别排序再按排名合并（RRF，k=60）：中文按两个字一组切词的 BM25、对夜间整理补的别名做 BM25、原有的子串检索。
- **夜间补别名**：夜间整理时对新的或改过的记忆调一次不带工具的模型，要几个同义词和另一种语言的说法，存进 `assistant.db`；记忆内容改了，旧别名自动失效。
- **按事件预取**：每个回合的提示里放最多 3 条和事件相关的记忆，标明只当参考；新建的 worker 不再拿到内置的 `recall`。
- **评估**：固定的 24 条记忆、44 个问题，前 3 条命中：子串 12，BM25 22，三路 39。别名和问题是同一个人写的，最后这个数偏乐观；剩下 5 个问题和记忆没有共同的词，留给下一步的本地向量检索。

D8 是第二步，本地向量检索，仍然不加 Go 依赖：

- **语义一路**：加 `-embed ollama`（默认关）后，本机 Ollama 用 `qwen3-embedding:0.6b` 给每条记忆算向量，存进 `assistant.db`；记忆改了重算，删了清掉，换模型全部重算。问题的余弦相似度不低于 0.35 才算命中，作为第四路并进 RRF。
- **退路**：Ollama 没开或出错时退回三路词面检索；连续失败 3 次列进「需要你处理」，恢复后自动清掉。
- **预取更严**：只有关键词或别名命中、或相似度不低于 0.45 的记忆才预取；只有子串命中的不算。
- **评估**：同一套 44 个问题，单用语义一路 43 个，四路 44 个（MRR 0.977），D7 的三路是 39 个。新加的 8 个没有答案的问题里，6 个能搜出东西，1 个被预取。两个阈值是在这套数据上选的，数字偏乐观。

D9 是第三步，带有效期的事实，不加依赖：

- **事实表**：人物和组织、它们的别名（名字和邮箱）、事实三张表。事实带开始、结束和被哪条替换；经理、公司、职位同一时间只有一个值，新值出现时旧值自动过期。
- **来源**：联系人表（经理、邮箱域名对应的公司）、收件箱和日历（联系人发过哪些信、组织哪些会）不用调模型，陌生人不会成为实体；你在信道里说的话由夜间整理调一次不带工具的模型提取，从你说的那一刻算起。你说的优先于联系人表，联系人表优先于邮箱域名。
- **用法**：画像的经理一项改成当前事实的视图；`memory_search` 先列出问题涉及的事实和有效期；第五路按问题里提到的人给记忆排序；说的是已被替换情况的记忆带「可能过期」标注；每回合按事件预取最多 4 条事实。

D10 接上三种真实信道（2026-11-11 拍板），默认都关，不加依赖：

- **信道**：你的 Telegram bot 私聊、Discord bot 私信，或者一个专给助理用的邮箱。你在那边发的话进页面同一个 chat thread，和在页面上打字一样；回复提问的那条消息就是回答这个提问。助理和系统的话按顺序同步过去。
- **只认你本人**：Telegram 和 Discord 按你的用户 ID；邮件要求发件人是你的地址，而且收信服务器写的最上面一条 `Authentication-Results` 里，你域名的 DKIM 或 DMARC 通过。
- **批准仍只在本机网页**：审批卡片会同步过去，但写明要到网页上批准。
- **验收**：用本地假服务把三种信道接到真守护进程上跑通：提问用 Telegram 和 Discord 的回复回答、伪造认证和陌生人的邮件被拒收、暂停时不往外发、恢复后按顺序补发、停机期间发来的消息重启后只处理一次。
- **评估**：固定的 11 个时间敏感问题。只看排第一的记忆，5 个是当前值、5 个是旧值；看第一条事实，11 个全是当前值；前 3 条里 8 条过期记忆全部被标注。提问用的说法正好是离线脚本模型的提取规则能认的，数字偏乐观；真模型的提取没有测。

现在的闭环是：

> 外部收件箱（模拟 MCP）→ `mail_poll` 轮询 → SQLite 触发器 → 规则快路径和准入分级（推断候选先分诊，默认只记录）→ Thread 订阅的 worker → 带闸门的工具（读经 MCP，只能起草，可以建任务）→ 待批准提案 → 人工批准 → 发件箱经 MCP 执行（同一幂等键重试）+ 账本
>
> 任务的检查时间到了，或者同一 thread 的提案有了结果 → `task.wakeup` 触发器 → 同一个 worker 核对 → 完成，或约下一次检查；连续几次没有进展，看门狗提醒用户
>
> worker 开后台准备 → 只读会话收集材料 → `job.done` 触发器回到原 thread
>
> 每晚 23:30 夜间整理 → 联系人、会议时间、去重记忆、检索别名、带有效期的事实、用户画像 → 画像、按事件预取的事实和相关记忆写进之后每个 worker 的提示

守护进程或 MCP 子进程被 `kill -9` 后，状态都能恢复，已批准的发送也不会重复。后续路线的顺序：

1. 硬化本机常驻底座（Keychain 凭据、备份、日志轮转）；
2. 把审批和账本做成可上线的形态；
3. 用真实的邮件和日历 MCP server 替换模拟 server，先读后写；
4. 增强主动性（D5 已做准入分级、分诊、后台准备和看门狗；以后接真实模型时再校准分诊）；
5. 做长期记忆（D6 已做链式召回、夜间整理和用户画像；D7、D8、D9 做了混合检索、本地向量检索和带有效期的事实）；
6. D10 已接 Telegram、Discord 和邮件三种信道，默认关；在手机上批准（带按钮的审批卡片）留到 P2 给信道加认证以后再做。

D11 回答了「这个助理只能给一个人在自己 Mac 上用吗」：是的，D0–D10 都是单用户守护进程。D11 加了一个默认关的 `fleet` 子命令，在一个进程里托管很多用户的助理，用户闲着时助理睡下，不占 goroutine、内存和文件句柄；最贵的模型调用由全局闸门和每日额度管住。多机分片、对象存储和自助注册只有设计，没有实现。

`deepagents-server` 不作为这条路线的底座，只作为持久任务语义的参考实现，原因见第 4 节。

## 2. 参考架构摘要

文章把持续在线、事件驱动的 Agent 称为 Super-agent，并归纳了四个特征：连续、高效、主动、持久。支撑这四个特征的是五个模块：

| 模块 | 要点 | 在个人助理里的含义 |
|---|---|---|
| 双层架构 | 常驻 Router（轻量模型、不带 bash）只负责交互和分派；Worker 上下文隔离，配最强模型和全套工具 | 用户面对的始终是同一个助理，后台每件事各由一个 worker 办 |
| 事件驱动 | Trigger 先过程序规则（快路径），再交给模型判断（慢路径）；同一话题的事件归入 Thread，订阅后直接送达 worker；上下文按 Inline & Spill 和链式召回组织；可投机执行 | 新邮件、邀约、日程提醒都是 Trigger；收到邀约时提前查冲突并起草回复 |
| 面向人的交互 | 异步 start/stop，不阻塞对话；IM 回复不超过 100 词 | 只在需要决定或验收时打扰用户 |
| 计算、状态、环境分离 | 计算无状态，状态进数据库，执行环境留在原地，用 daemon 接入 | 笔记本合上后照常运行；状态可以恢复 |
| Watchdog | 外部的控制回路，既盯基础设施，也盯任务有没有实质进展 | 发现卡住或跑偏的 worker |

### dsh-superagent 原型给的启发（2026-11-01 对照）

原型的核心原则是「尽量少占用人的注意力，尽量多给价值」。领域模型是 Source → Trigger → Thread → Eval → Ticket（带 Mandate）→ Assignment → Executor。下表是逐条对照（事实来自原型文档，「做法」一列是建议或本轮已做的事）：

| 原型里的机制 | 我们原来的状态 | 做法 |
|---|---|---|
| 面板先回答「现在有没有事需要我」，健康状态不占位置；数字必须等于它链接的列表长度 | 页面按组件分标签，待办散在信道和任务页里 | **D3 已做**：「需要你处理」列表，由 `assistant.db` 和内存健康看板推导 |
| 暂停处理：停派工、停投递、停回复；Source 继续记录；正在跑的回合不打断 | 没有 | **D3 已做**：持久的暂停开关，跨重启保持 |
| 并发上限之外，给人的消息多留一个槽位，唤醒优先于新任务 | 4 个 worker，按触发器 ID 先来先领 | **D3 已做**：聊天先领取，另留 1 个只跑聊天的槽位 |
| 只重试暂时性故障（408、429、5xx、连接问题），失败要如实上报 | 任何错误都重试 3 次；模型失败被当成回复发出 | **D3 已做**：同时修了模型失败被发到信道的缺陷 |
| 组件连续失败 3 次才算问题，一次网络抖动不打扰人 | 页面只有即时错误徽标 | **D3 已做**：内存健康看板 |
| 启动时锁住状态目录，防止第二个进程迁移或写同一份状态 | P1 计划给队列加通用租约 | **D3 已做**：`daemon.lock`。P1 的跨进程租约留给以后多主机的情况 |
| 同一 Thread 一次只跑一个 Eval，期间到达的触发器并成下一批 | 同一 thread 串行，但每个触发器各跑一回合、各发一条消息 | **D4 已做**：领取时把同一 thread 积压的同类触发器合并成一回合 |
| Executor 用结构化报告（progress / waiting / ready / blocked / failed / dropped）加最多一个具体问题，不从自由文本推断「在等人」 | worker 用 `[QUIET]` 前缀表示不打扰 | **D4 已做**：`report` 工具（notify / ask / quiet），ask 只带一个问题，回答回到原 thread |
| 接受模式 off / observe / auto：主动工作先只记录「本来会接」，看对了再放开 | 没有自动批准 | **D5 已用于推断候选**：观察 / 自动两档，默认观察。**建议 P2**：自动批准策略也先跑 observe，只记账不执行 |
| Mandate 记下接单依据和 Policy 版本；规则变了，受影响的工单收到通知，恢复前重新校验 | 没有策略版本 | **建议 P2**：自动批准记录命中的规则和版本，规则变更后重新校验挂起项 |

## 4. 运行时选择：为什么 Go 优先，`deepagents-server` 是什么角色

**`deepagents-server` 的角色**（事实）：它是仓库里独立、需显式启用的参考模块，有自己的环境、依赖锁和部署配置，并且明确「不调用已有 `mini_loop` Python/Go runtime」。它承担两件事：

1. 用 LangChain Deep Agents 和标准 LangGraph Agent Server 复现 Managed Agent Server 的分层，参考设计见 [MDA 设计](MANAGED_DEEP_AGENTS_AGENT_SERVER_DESIGN.md)；
2. 用 Temporal Task HTTP 服务验证长任务的持久语义：幂等提交、202 只在远端确认 Start 后返回、取消、冷重启恢复、Continue-As-New、优雅排空、容器加固。

它有意不包含 mini-loop 的 ToolGate、审批、hooks 和 SQLite schema，Task 运行时里也没有真实工具和 owner 记忆。

**上一版建议的修正**：上一版曾建议以 Temporal task server 为底座，理由是当时只有它被验证过能扛住进程死亡。现在有了新的前提：Go 优先、单用户个人助理，而且 demo 已经验证「SQLite + 守护进程」能扛住 `kill -9`。在这个前提下，改为如下建议。

**建议：以 Go 运行时为底座**，理由如下：

- **治理已经在 Go 里**：风险分级、权限、action journal、owner 记忆、typed extension、SQLite 状态都有。如果放到 `deepagents-server`，等于在第三套代码里重新移植这些治理能力。
- **运维简单**：单个二进制、goroutine 并发、`mattn/go-sqlite3` 是唯一的依赖。一个用户一台常开主机就够，不需要额外运行 Temporal 集群和 PostgreSQL。
- **不新增依赖**：Temporal Go SDK 属于新增依赖，需要单独审批。只有出现多主机高可用需求时，再把触发器队列后端替换为 Temporal；路线里会保留这个替换的接口位置。

**从 `deepagents-server` 借鉴的部分**（建议）：

- 「owner + 幂等键 → 任务 ID」；
- 「持久接纳后才返回 202」；
- 冷重启验收场景；
- SIGTERM 排空；
- 非 root、只读根文件系统的容器配置；
- `task_contracts.py` 里的 admission、fencing、`dispatch_unknown` 状态，作为触发器队列扩展到多进程时的设计参考。

## 5. 分阶段路线（Go）

顺序原则沿用 [Agent Platform Roadmap](AGENT_PLATFORM_ROADMAP.md)：先持久和闸门，再接外部世界，最后才主动。每个阶段都要求测试、`-race`、架构图和账本证据。

### D0 — 可运行 demo（已完成）

见第 3 节。边界：模拟信道、模拟数据、无认证、只监听回环地址、离线脚本模型（可选真实模型）。

### D1 — 本机常驻 + 模拟 MCP（已完成）

- **集成**：`miniloop-assistant mock-mcp` 是同一个二进制的子命令，在子进程里用 stdio JSON-RPC 提供 9 个工具：
  - 读：`mail_list`、`mail_read`、`calendar_list`、`calendar_get`；
  - 轮询：`mail_poll`；
  - 效果：`mail_send`、`calendar_respond`，都按 `idempotency_key` 幂等；
  - 模拟外部世界：`sim_deliver`、`sim_deliver_custom`。

  守护进程经 `go/mcp` 的 stdio 客户端调用它，子进程死后会在下一次调用时被重启。
- **触发**：轮询器每 2 秒拉一次 `mail_poll` 游标；网页投递后立即唤醒轮询器，不再直接写触发器。
- **发件箱**：批准后的提案进入 `approved` 状态，由发件箱经 MCP 执行；记下回执，或者记下失败并退避。
- **本机部署**：默认数据目录放在 Application Support；`launchd-plist` 子命令输出 LaunchAgent，安装和卸载命令见 `go/assistant/README.md`。
- **边界**：
  - 模拟 server 和模拟信道仍然没有认证，只监听回环地址；
  - launchd 下只支持离线脚本模型；
  - 一个数据目录只能跑一个守护进程。

### D2 — 持久任务 + 自我约定检查 + 日程临近（已完成）

- **任务**：`assistant.db` 新增 `tasks` 表。worker 有 4 个任务工具：`task_create`、`task_schedule`、`task_complete`（都是 `write` 风险，只改本地状态）和 `task_list`（`read`）。任务绑定创建它的 thread 和 worker session；用户在页面上可以「立即检查」或「取消」。
- **唤醒**：scheduler 每轮领取到期任务。领取、计次、入队 `task.wakeup` 触发器和设置兜底检查（30 分钟后）在同一事务里完成。触发器走同一 thread 的订阅，所以醒来的是原来的 worker，带着原来的上下文。
- **事件联动**：同一 thread 上的提案发出、被拒或最终发送失败时，任务检查提前到现在，并把原因写进唤醒提示。
- **边界**：
  - 每个任务最多自动检查 6 次，之后转交给用户；最多 20 个活跃任务；检查间隔 1 分钟到 7 天；
  - 处理外部邮件的 worker 只能改自己 thread 上的任务；
  - 任务检查和其他触发器一样是 untrusted 回合，只能起草，不能直接产生对外效果。
- **日程临近**：scheduler 每轮经 MCP `calendar_list` 查看接下来 15 分钟。每个已确认的会议按（event_id，开始时间）只提醒一次；已经开始的会议不补提醒。模拟器新增 `sim_add_event`，可以加一个马上要开的会。
- **并行**：不同 thread 并行、同一 thread 串行，这在 D0 就已经实现，这轮补了测试和页面上的运行中 worker 数。
- **还没做**：任务依赖和子任务、由模型自己调整检查预算。（判断「有没有实质进展」的看门狗在 D5 完成。）

### D3 — 少打扰、可暂停、你优先（已完成）

借鉴 `dsh-superagent` 原型（见第 2 节）。

- **需要你处理**：页面顶部一个列表，只列等你的事：待批准的草稿、最终发送失败的提案、用完 6 次检查转交给你的任务、24 小时内失败的触发器、连续失败 3 次的组件（收信轮询、日程查看、发件箱传输、worker 模型调用）。每项直接带操作：批准或拒绝、重试发送（同一幂等键）、再跟进一轮（再给 6 次检查）、重新处理、知道了。没有待办时整块隐藏。
- **暂停**：`assistant.db` 里一个持久开关。暂停时 router 不领取、发件箱不发、scheduler 不领取 routine、任务检查和提醒；轮询照常收信，页面照常记录决定，正在跑的回合会跑完。恢复后按停机补跑，暂停期间已经开始的会议不补提醒。
- **你优先**：聊天触发器先被领取；`-workers` 之外再留 1 个槽位，只跑聊天。
- **失败分类**：agent 会话把模型调用失败和回合耗尽当作最终文字返回。router 现在从本回合的会话事件里识别出这两种情况，按失败处理，不再发到信道。MCP 拒绝、4xx 模型拒绝（凭据、权限、无效请求）和回合耗尽直接失败；断网、过载、限流和超时最多尝试 4 次，带退避。
- **单守护进程**：数据目录里的 `daemon.lock`（`flock`，进程退出时由内核释放）拒绝第二个守护进程。
- **边界**：
  - 健康看板只在内存里，重启后要重新连续失败 3 次才会出现；
  - 卡住检测器的停止文字仍会发到信道，因为 agent 没有公开这个事件的读取接口；
  - 锁只在 macOS 和 Linux 上生效；MCP 子进程在检查锁之前启动，被拒绝的第二个守护进程会短暂打开同一个 `world.db`。

### D4 — 合并回合、结构化汇报、会提问（已完成）

借鉴 `dsh-superagent` 原型（见第 2 节）。

- **合并回合**：router 领取一个 thread 最早的待处理触发器时，把这个 thread 其余已到期、同一信任等级的待处理触发器一起领取（最多 8 个），交给 worker 一个回合处理，只汇报一次。用户的聊天是显式人类授权，其余都是 untrusted，所以聊天不和别的类型混在一批；routine 总是单独跑。被规则或状态检查排除的触发器单独结束。草稿、任务和提问都记在批次里最早的触发器上，崩溃后重跑会收敛到同一批记录；回合失败时整批一起重试或一起失败。
- **结构化汇报**：新的 `report` 工具（本地写，风险 `write`）。notify 把结论发到信道；ask 只带一个具体问题，进入「需要你处理」；quiet 不发信道，原因写进账本。quiet 但起草了提案时，卡片照样发，因为它们需要用户决定。不调用 report 的回合按 notify 发出最终文字，账本记下缺少 report。router 仍然是唯一写信道的组件。
- **提问与回答**：问题存在 `assistant.db` 的 `questions` 表里，每个批次最多一个。用户在「需要你处理」里回答后，回答作为 `user.answer` 触发器回到提问的 thread，由订阅它的同一个 worker 接着处理。这个回合仍按 untrusted 执行：回答是用户亲口说的，但这个 thread 的上下文里有外部邮件。
- **边界**：离线脚本模型对连发的聊天只回答最后一条；真实模型会看到整批。

### D5 — 准入分级、分诊、后台准备、看门狗（已完成，即 P5）

- **准入分级**：规则快路径先忽略批量邮件，再按「发件人是不是已知联系人」×「是不是直接写给你」分级。联系人存在 `assistant.db` 的 `contacts` 表里，预置经理、同事、朋友和云服务商 4 人；发件箱每发出一封，收件人的往来次数加一，新地址成为联系人。非邮件触发器都算明确请求。
- **分诊**：推断候选先过一次 `Purpose=decision`、不带工具的模型调用，只看发件人、收件人、主题和预览（包在 `<external>` 里），回答 handle、observe 或 ignore 加一句理由。候选模式存在 `assistant.db` 里，默认观察：handle 也只把触发器标成 `observed`；页面「候选」里「交给 worker」把它重新排队并标成已准入，router 不再分诊；「忽略」直接结束。自动模式下 handle 直接派工。分诊失败或答复读不懂时只记录。
- **后台准备**：`prepare_start` 把一个准备任务写进 `jobs` 表（按触发器和目标去重，排队加运行最多 5 个）。Preparer 一次跑一个，每个任务开一个新会话，工具目录只有 `mail_list`、`mail_read`、`calendar_list`、`task_list`，按 untrusted 执行，最长 2 分钟。完成或失败时在同一事务里给原 thread 入队 `job.done` 触发器；被取消的任务不再唤醒。页面「停止」或同一 thread 的 `prepare_stop` 取消任务；重启时把在跑的任务放回队列；暂停期间不领取。
- **看门狗**：每个 `task.wakeup` 回合结束后，在 `task_checks` 表里记下任务当时的「要核对」和「进展」。scheduler 每轮之后，用 `agent.NewStuckDetector` 读最近的快照：同样的核对内容和进展连续 3 次，或在两种状态之间来回 6 次，就记账、发一行信道消息，并在「需要你处理」里列出（立即检查 / 取消任务 / 知道了）。之后有进展就清除；新一轮又会提醒，即使之前点过「知道了」。
- **验收**：`TestSyntheticEventStreamAcceptance` 按权重混合 15 种事件，共 300 条，报告延迟分位、router 决定计数和安静率；`MINILOOP_ASSISTANT_STREAM_REPORT` 指定路径时保存 JSON。
- **和原计划的差别**：
  - 异步 start/stop 用持久的 `jobs` 表加守护进程里的一个 goroutine，没有用 `go/background`，因为 worker 没有 shell，后台准备也只该读；
  - 「LLM Router」只用于推断候选，明确请求不等分诊；
  - 投机执行只演示了账单核对，而且准备会话不能起草；
  - router 的决定计数只在内存里，重启后清零。
- **边界**：离线脚本模型的分诊是关键词规则，只用来演示这条路径；300 条事件流的数字来自离线模型，不代表真实模型的延迟。

### D6 — 链式召回、夜间整理、用户画像（已完成，即 P6）

- **链式召回**：`lookup` 是只读工具，按引用读 `assistant.db` 里的一条记录。触发器返回类型、状态、thread、摘要和决定，下一跳是它的 thread、worker session、它产生的草稿/任务/提问/准备任务，以及它引用的任务、提问或准备任务；任务、提案、提问、准备任务返回自己的字段，下一跳是触发器、thread 和 session；`thread:` 列出最近的触发器和订阅的 worker；`session:` 列出这个 worker 处理过的触发器。摘要可能引用外部邮件，只当数据。
- **夜间整理**：`夜间整理` routine 在 23:30，用自己的 meta key 预置，旧数据目录也会有。router 处理它时先跑 `Consolidator.Run`：最近 30 封已发送邮件的收件人记成联系人（来源「夜间整理」）；读未来 7 天日历，记下已确认会议的时间窗；记忆按「忽略大小写、空格和标点后的正文」去重，优先保留明确说过的、其次 feedback 类型的，只有真有重复时才用 `ReplaceAll` 重写；重建画像并记一行账。然后 worker 回合看到这些结果和当天你在信道里说过的话，把偏好用 `remember` 记下，最后 report quiet。每一步都幂等。
- **用户画像**：`assistant.db` 的 `profile` 表有四项：经理、常联系、会议时间、偏好（前三条 feedback 记忆）。每个 worker 的提示里都有「用户画像」一段，标明只当参考、不是指令。启动时和夜间回合之后，守护进程会重建不需要日历的三项。
- **检索评估**：`TestLexicalMemoryRecallEvaluation` 在 10 条记忆上测现有的 `memory.Store.Search`（recall@3）：主题词 8/8，空格分开的关键词 4/4，换了说法的问题 0/8。原因是检索只在非字母处切词、每个词要作为子串出现。
- **和原计划的差别**：
  - 联系人只从已发送邮件学，不从来信学，避免陌生人写两封信就变成已知联系人、绕过分诊；
  - 去重只合并正文相同的记忆，不改写内容，也不合并意思相近的记忆；
  - 没有做语义检索：需要嵌入模型或向量库，属于新依赖，要先审批。
- **边界**：夜间回合和其他 routine 一样按 untrusted 执行，只被要求记你在信道里说过的话；worker 从邮件里记下的记忆仍可能进入画像的偏好一项，所以画像标明只当参考。离线脚本模型按关键词挑偏好。

### D7 — 混合检索第一步：中文两字切词 BM25、夜间补别名、按事件预取（已完成）

- **检索**：`MemorySearch` 每次查询现建索引，三路：名字、说明和正文上的 BM25（汉字、假名、韩文按重叠的两字切，其余按词，丢掉单个字母和少量英文虚词）；别名上的 BM25；`go/memory` 原有的子串检索。三路各自排名后按 RRF（k=60）合并，平分时多路命中的优先。Markdown 记忆文件仍是权威，`go/memory` 和 `go/agent` 没有改。
- **别名**：夜间整理在去重之后，对没有别名、或内容已经变了的记忆（每晚最多 12 条）调一次不带工具的模型（`memory_consolidation` 用途），要 3 到 8 个同义词、上位词和另一种语言的说法。`memory_aliases` 表按记忆名加内容哈希存，内容改了旧别名不再计入，删掉的记忆连同别名一起清掉。调用失败只记账（「别名生成失败，下次整理再试」），不影响整理的其余部分。离线脚本模型用一张小同义词表代替。
- **worker**：router 新建的会话只拿助理自己的工具、`remember` 和 `memory_search`，不再有内置的 `recall`。每个回合按事件（发件人和主题、你说的话、日程标题和组织者、任务标题）预取最多 3 条相关记忆，不超过 600 字，标明只当参考。从旧版本恢复的 worker 还是旧的工具目录。
- **页面**：「画像与记忆」写明检索方式，每条记忆下面列别名，加了一个试搜框，结果标出是哪一路命中的。
- **评估**：`go/assistant/testdata/recall_eval.json` 固定 24 条记忆、44 个问题，分主题词、空格关键词、整句提问、换说法、跨语言五类，`TestMemoryRetrievalEvaluation` 计前 3 条命中和 MRR@3：子串（旧 recall）12/44、MRR 0.273；BM25 22/44、0.500；BM25 加子串 22/44；三路 39/44、0.852。整句提问从 0/10 到 10/10 靠的是两字切词；换说法和跨语言靠别名。没找到的 5 个（不能吃什么、网断了打给谁、teeth cleaning、peanuts、牙科诊所）和记忆没有共同的词。
- **和原计划的差别**：
  - BM25 在 Go 内存里算，没开 SQLite FTS5：记忆只有几千条，每次查询现建索引就够快；以后要检索邮件和对话原文再开（需要编译选项 `sqlite_fts5`，不是新依赖）。
  - 新记忆要等当晚整理才有别名，在那之前只靠关键词和子串。
- **边界**：检索、预取和页面搜索都只读；预取的查询可能来自外部邮件的发件人和主题，所以邮件能影响 worker 看到哪几条记忆，但 worker 仍然不能不经批准发信。别名请求只把记忆内容发给配置的模型，离线模型不出进程。

### D8 — 本地向量检索（已完成）

- **嵌入**：`OllamaEmbedder` 用标准库 `net/http` 调本机 Ollama 的 `/api/embed`，记忆一次最多 16 条，按「名字 + 说明 + 正文」截到 1000 字送；问题前面加 Qwen3 要求的检索指令。`-embed off|ollama`（默认 off）、`-embed-url`（默认 `http://127.0.0.1:11434`）、`-embed-model`（默认 `qwen3-embedding:0.6b`）；`install` 生成的 plist 照传这几个参数，但 launchd 不负责启动 Ollama。
- **向量索引**：`VectorIndex` 把向量存在 `memory_vectors` 表（记忆名、内容哈希、模型、维度、float32 向量），内存里留一份。语义检索之前先同步：新的或内容变了的记忆重算，删掉的清掉；启动时第一次加载会删掉别的模型的向量。启动后先同步一次，再探测一次服务，所以重启后状态是真的，不用等第一次搜索。
- **检索**：查询向量和每条记忆逐条算余弦，不低于 0.35 的取前 10 个，作为「语义」一路并进 RRF；命中的结果带相似度，工具结果里是 `similarity="0.56"`，页面上是「相似度 0.56」。到十万条之前不需要向量库。
- **退路和健康**：嵌入出错时这一路跳过，其余三路照常返回；健康板记一次失败，连续 3 次就在「需要你处理」里显示「语义检索（本地嵌入模型） 连续失败 3 次」，下一次成功清掉。页面写明索引了几条、上次连上的时间，或者「语义检索已配置但暂时不可用（模型：原因），恢复后自动并入」。
- **预取**：只预取关键词或别名命中的、或相似度不低于 0.45 的记忆。只有子串命中的不再预取，因为没有答案的问题「what is my blood type」里的 is 匹配到了 English。
- **评估**：评估集加了 8 个没有答案的问题。`TestMemoryRetrievalWithOllama` 只在设置了 `MINILOOP_ASSISTANT_OLLAMA_URL` 时运行，用真模型扫 0.35、0.40、0.45 三个阈值；平时的测试用一个按概念给向量的假嵌入器。`qwen3-embedding:0.6b` 的结果（前 3 条命中，44 个问题）：

  | 阈值 | 只用语义 | 关键词 + 语义 | 四路，不用别名 | 四路，用别名 | 没有答案却搜出东西 | 没有答案却被预取 |
  |---|---|---|---|---|---|---|
  | 0.35（默认） | 43（MRR 0.955） | 43 | 43 | 44（MRR 0.977） | 6/8 | 1/8 |
  | 0.40 | 40 | 40 | 40 | 44 | 3/8 | 1/8 |
  | 0.45 | 37 | 38 | 38 | 42 | 2/8 | 1/8 |

  0.35 时只用语义漏了「out of office」；四路靠别名补上。被预取的那个是「家里的猫叫什么」，靠的是两字切词「家里」命中了接孩子那条。关键词加语义的 MRR 低于只用语义，说明 BM25 有时把对的结果挤到第二。
- **和原计划的差别**：
  - 阈值是在同一套评估集上挑的，没有另留一套验证集；没有答案的问题只有 8 个，误报率的估计很粗。
  - 新记忆的向量在下一次语义检索时现算（大约 60 毫秒），不在写入时算。
- **边界**：开了以后，记忆内容和查询（包括来信的发件人和主题）会发给 `-embed-url`。默认是回环地址；填别的主机，记忆就会经网络发出去。向量和别名一样是派生数据，可以删掉重建。

### D9 — 带有效期的事实（已完成）

- **三张表**：`entities`（人物和组织）、`entity_aliases`（小写的名字、邮箱、域名，第一个认领的实体拥有它）、`facts`（主语、谓词、宾语实体或取值、`valid_from`、`valid_to`、`superseded_by`、来源、证据）。谓词是固定的：`manager`、`works_at`、`role` 同一时间一个值；`wrote`、`organizes` 是往来记录，每人每种只留最近 5 条。
- **不用模型的来源**：启动和夜间整理时，联系人表里每个联系人是一个实体，按邮箱和名字认；工作邮箱的域名对应一个组织（acme.example 叫 Acme，也认 acme），朋友、家人和免费邮箱不算；标为经理的联系人是你的经理。夜间整理还从收件箱和日历里记下联系人发过的信和组织的会。陌生人不建实体，所以来信改不了事实。事实从联系人加入的时间、来信或会议的时间算起。
- **模型提取**：夜间整理把上次之后你在信道里说的话（最多 40 句，带序号和时间）发给模型，不带工具，要求按「序号 | 主语 | 谓词 | 宾语」输出 manager、works_at、role 三种事实。格式不对、谓词不在表里、序号越界、名字太长的行都丢掉；事实从你说那句话的时间算起，证据记信道消息号。成功后游标前移，失败只记账（「事实提取失败，下次整理再试」），下次连同积压一起再问。离线脚本模型用几条固定句式代替。
- **时间线和优先级**：同一主语同一谓词按开始时间排成时间线；新事实结束于下一条开始时，前一条结束于它开始时，所以晚到的旧事实会插到中间。来源分三级：你说的 > 联系人表 > 邮箱域名、收件箱、日历；更弱的来源给出的新值不会替换更强来源的当前值。已经记过的（当前的，或同一开始时间的）不再写，重跑收敛。
- **用法**：
  - 画像的经理一项是当前事实的视图，带开始日期和上一任；联系人表里标为经理但已不是当前经理的人在「常联系」里显示为前经理。
  - `memory_search` 先列出问题涉及的事实：问题里提到的人的事实、指向他们的事实，问到「我的经理」这类时加上你自己的事实；问了某个谓词就只列这个谓词。当前的单值事实在前，然后是已替换的，最后是往来记录，最多 6 条。
  - 第五路「人物」：问题里提到的人，加上你自己当前的经理（问「我老板」时），按记忆里提到几个排序。邮箱只算它自己的实体，alice@acme.example 不算提到 Acme。
  - 记忆里出现了已被替换的值、对应谓词的词，以及主语（是你自己时不需要），就带上 `outdated="我的经理自 2026-11-02 起是 Carol，不再是 Alice"`；页面上是「可能过期」。
  - 每回合按事件预取最多 4 条事实，标明只当参考；worker 的系统提示要求事实和记忆冲突时以当前事实为准。
  - 页面「人物与事实」表列出全部事实，已替换的划线并写明被谁替换。
- **评估**：`testdata/facts_eval.json` 有 4 个联系人、两个月里说过的 8 句话（同时记成记忆）和 11 个时间敏感问题。`TestFactsEvaluation` 用离线脚本模型的提取：排第一的记忆是当前值 5 个、旧值 5 个；第一条事实 11/11 是当前值（包括一个没有答案、也不该编出答案的问题）；前 3 条里的 8 条过期记忆全部带标注。说法是按提取规则写的，事实这一项偏乐观。D7 的词面评估不受影响（评估库里没有事实），仍是 39/44。
- **和原计划的差别**：
  - 用户画像只把经理一项改成事实视图，常联系、会议时间、偏好三项照旧。
  - 模型只从你在信道里说的话提取，不读记忆文件：记忆没有时间戳，worker 从邮件里记下的记忆也不该改事实。
  - 同名的人会合并成一个实体，没有做消歧。
- **边界**：事实是派生数据，不改 `memory/`；提取请求只把你最近说的话发给配置的模型，离线模型不出进程。

### D10 — 真实信道：Telegram、Discord、邮件（已完成）

- **开关和密钥**：`-telegram-chat <你的用户 ID>`、`-discord-user <你的用户 ID>`、`-email-owner <你的地址>`（再加 `-email-user`、`-email-imap`、`-email-smtp`、`-email-authserv`），都默认关。bot token 和邮箱密码只从 `MINILOOP_TELEGRAM_TOKEN`、`MINILOOP_DISCORD_TOKEN`、`MINILOOP_EMAIL_PASSWORD` 读；这些名字符合凭据形状，MCP 子进程拿不到；`launchd-plist` 拒绝这些参数。
- **收**：
  - Telegram 用 `getUpdates` 长轮询（25 秒），只收你和 bot 的私聊：会话 ID 和发送者 ID 都等于你的用户 ID，群聊和别人的消息拒收。打开会话时的 `/start` 不算。
  - Discord 不连 gateway（那要 WebSocket 依赖），每 3 秒经 REST 读 bot 和你的私信；bot 读私信内容不需要特权 intent。
  - 邮件每 30 秒经 IMAP 读收件箱，只用 `EXAMINE` 和 `BODY.PEEK[]`，不标已读、不移动、不删除。一次最多 20 封，超过 256 KB 的拒收，取第一个纯文本部分（没有就取 HTML 的文字），去掉引用的原文和签名；不是 UTF-8 的拒收并请你用 UTF-8。
- **怎么认出是你**：Telegram 和 Discord 由服务验证账号，按你的用户 ID 认。邮件的发件人很容易伪造，所以要两条都满足：发件人是 `-email-owner`；最上面一条 `Authentication-Results`（收信服务器加在最上面，下面的可能是发件人自己写的）由 `-email-authserv` 写出，并且你域名的 `dmarc=pass`，或者由你域名签名的 `dkim=pass`。
- **进对话**：每次收取，把消息、去重记录（按服务里的消息 ID）和服务游标在同一个事务里写进 `assistant.db`；重复收到的消息按 ID 跳过，崩溃不丢也不重复。信道消息带来源标记，作为 chat 触发器进入同一个 chat thread，权限和在页面上打字一样是 explicit-human。回复的是一条仍在等待回答的提问，就当作回答交回提问的 thread。第一次启用时从服务里最新的消息开始，不回放旧消息。暂停时照常收录。
- **往外发**：助理和系统在信道里说的话（不含你自己的）按信道顺序发到每个启用的远程信道，每个信道有自己的投递游标。服务接受后才前移游标，所以崩溃在两者之间会把那一条再发一次；发送失败就停下这一轮，保证顺序；服务因为内容拒收（HTTP 400，或 SMTP `DATA` 之后的 5xx）的那条跳过并记账。暂停时不往外发。提问后面加「（直接回复这条消息即可回答）」，审批卡片后面加「（到本机助理网页批准或拒绝；这里不能批准）」。长消息按服务的上限拆成几条，邮件一条一封。
- **状态**：页面顶部每个信道一个标记，收或发失败时变红；连续失败 3 次进「需要你处理」；账本新增 `remote` 记录。Telegram 的 token 在请求路径里，所有错误里都换成 `<token>`。
- **验收**：单元测试用假的 Bot API、Discord REST、IMAP 和 SMTP 服务覆盖拒收、去重、回复回答、暂停、拒收跳过和认证头的各种情况（包括伪造在下面的通过记录）。另外用本地假服务把三种信道接到真的守护进程上：Telegram 发「记住 …」三个信道都收到回复；同事来问的提问用 Telegram 和 Discord 回复回答，起草的回复卡片同步过去，提案仍待在网页上批准；伪造认证和陌生人的邮件被拒收并记账；暂停时一条都不发，恢复后按顺序补发，包括到点的提醒；停机期间在 Discord 发的消息重启后只处理一次，之前的消息没有重发。没有接真的 Telegram、Discord 或邮箱账号。
- **和原计划的差别**：
  - 原计划 P4 只接一个信道，并且带按钮在手机上批准；这次按要求接了三个，但批准仍只在本机网页，因为远程信道的账号一旦被别人控制，就能替你发邮件。
  - Discord 用 REST 轮询代替 gateway，延迟最多 3 秒，换来不加依赖。
  - 没有做群聊、附件、图片、语音和 webhook（守护进程只监听回环地址，收不到推送）。
- **边界**：远程信道的消息有和页面一样的权限：控制了你的 Telegram 或 Discord 账号、或者能发出通过你域名认证的邮件的人，可以以你的身份聊天、回答提问、取消任务，但不能批准。同步出去的话会经过 Telegram、Discord 或你的邮件服务商，可能带着邮件主题、人名和日程。

### D11 — 多租户 fleet：一个进程托管很多用户，闲时睡下（已完成）

- **为什么**：D0–D10 是单用户守护进程：一个数据目录、页面只听回环地址、没有认证，每个用户一直开着 8 个 goroutine 和几个定时循环。照这个形态做云服务，就是一人一个常驻进程，1000 个用户闲着也要占约一个 CPU 核和 1 GB 以上内存，模型调用也没有上限。
- **形态**：`miniloop-assistant fleet` 默认关，必须给 `MINILOOP_FLEET_ADMIN_TOKEN`（至少 24 个字符）。
  - 每个租户还是原样的单用户 App，有自己的目录 `tenants/<分片>/<id>/`：`assistant.db`、`agent.db`、记忆和模拟世界都是自己的，租户之间不共享表。
  - `fleet.db` 每个租户一行：令牌哈希、状态、下次唤醒、最近访问，另有每天的模型调用数和 token 数。
  - 根目录的 `daemon.lock` 挡住第二个 fleet。
- **省模型（最贵）**：
  - 全局闸门限制同时跑的回合数（`-turns`，默认 8），留四分之一给用户的聊天。router 和后台准备先要名额再认领工作，排队的工作不耗重试次数；有聊天在等时，后台工作让路。
  - 每次调用按租户和天计量。超过 `-daily-calls`（默认 200）的租户停到第二天：聊天返回 429 和恢复时间，通知用户一次；读取和批准照常。
  - 用户离开超过 `-dormant-after`（默认 7 天），不再为他唤醒，例行任务不再花钱。
  - 新装的助理不再补跑安装前已经过去的例行时段。压测发现，晚上建的每个租户都会立刻补跑晨报和夜间整理，每个租户 9 次调用；修好后是 2 次（就是那次聊天本身）。单用户守护进程同样受益。
- **省计算**：只有用户在用或者有事到点时助理才开着。
  - 安静（没有回合在跑、没有可认领的工作、下一个定时器之前无事）并且用户离开超过 `-idle`（默认 2 分钟）就睡下。睡前把最早的例行时段、任务检查、日程提醒和已批准效果的时间写进注册表。
  - 唤醒器按注册表打开到点的租户。开着的数量到 `-max-active`（默认 256）时，用户请求会挤掉最久没用的安静租户；唤醒器从不挤人，并给用户留八分之一的位置。
  - 进程崩溃时开着的租户，下次启动立即到点，打断的工作接着跑。用户离开 10 分钟，助理既不安静、也没在跑或等回合，就关掉，5 分钟内不再唤醒。
- **省存储**：注册了但没用过的租户在磁盘上是 0 字节；睡下时 SQLite 合并 WAL，只留主库文件；离开超过 `-archive-after`（默认 30 天）压成一个 `.tar.gz`，下次请求时解压（目录还在就以目录为准）。解压只接受目录和普通文件，拒绝绝对路径和 `..`，最多 4 GiB。
- **入口**：`/t/{id}/` 用该租户的 bearer 令牌（只存 SHA-256，常量时间比较），未知租户和错误令牌都返回 401，避免探测 ID；`/admin/` 用管理令牌建、列、查、删租户和看统计；`/healthz` 免认证。页面本身不带租户数据，从链接的 fragment 读令牌放进标签页的 `sessionStorage` 并从地址栏去掉；API 路径改成相对路径，标签页隐藏时停止轮询。每个租户每秒 20 个请求（突发 40）。非回环地址必须给 `-tls-cert/-tls-key` 或 `-behind-tls-proxy`。
- **验收**：
  - 单元测试覆盖：懒创建和睡到下一个定时器、为例行任务唤醒、崩溃恢复、按 LRU 挤出、每日额度、聊天优先的闸门、卡住的租户被关掉、休眠和归档、目录优先的恢复、归档解压不越界、每个租户请求都要认证、令牌桶、第二个 fleet 被拒。CLI 测试覆盖不安全启动被拒和完整的建租户、聊天、关机流程。
  - `MINILOOP_FLEET_LOAD=1000` 压测（`GOMAXPROCS=2`，脚本模型，32 个客户端，`-max-active 64`）：1000 个租户各自读状态、聊一次后离开，没有 503。全部睡下后 1000 个租户合计空闲 CPU 2.9 ms/s，常驻 50 个时每个 1.0 ms/s；磁盘每个租户 312 KB（常驻开着 808 KB），归档 15 KB；唤醒睡着的租户在压力下 p50 351 ms、p99 950 ms，热读 p50 0.5 ms，从归档恢复 p50 5 ms。每个开着的租户约 13 个文件句柄，睡着为 0。
  - 浏览器里用管理 API 建租户，打开链接：令牌从地址栏消失，聊天正常，23:54 新建的租户没有补跑晨报；用户离开后租户睡下，下次唤醒是第二天 07:00，目录里没有 WAL 文件。单用户守护进程的页面照常可用。
- **和原计划的差别**：原路线只有单用户本机部署（P1）。D11 按用户要求先做了单机多租户；多机分片、对象存储、自助注册都只写了设计。
- **边界**：
  - 一个 fleet 只有一个时区和一个模型；fleet 里的租户没有远程信道和向量检索；邮件和日历仍是每个租户一份模拟世界，在进程内而不是子进程。
  - 租户令牌和在该租户页面上打字的权限一样，包括批准；目前不能轮换，只能由管理员删除租户。
  - fleet 不对未认证请求限流，令牌桶在租户重新打开时重置，所以要放在按地址限流的代理后面。
  - 睡着的租户只为它记下的定时器醒来。真实邮箱的新邮件需要 `-sweep` 或服务商推送。页面仍每 1.5 秒拉一次完整状态（可见时）；用 ETag 或推送变化可以再省。
  - 额度按调用次数计，不按 token。Go 堆不会立刻还给系统：压测后全部睡下时 RSS 仍比开始高 87 MB。

### P1 — 本机常驻底座硬化（Own computer）

- **凭据**：从 macOS Keychain 读取模型和连接器凭据（launchd 不继承 shell 环境），接上 `secrets.Registry` 遮蔽；修掉 launcher 不设置 `ManagerServices.Secrets` 的缺口。
- **运维**：SQLite 定时备份、账本保留策略、launchd 日志轮转；`doctor` 子命令检查 LaunchAgent 状态、端口、数据目录和 MCP 子进程。
- **租约**：D3 已用数据目录独占锁解决「同一数据目录两个守护进程」的问题。通用租约（沿用 `sqlitestate/lease.go` 的条件 UPDATE 模式）留到触发器队列需要跨主机共享时再做。
- **推迟**：Linux 容器镜像和 systemd 单元，等需要换到常开主机时再做。
- **验收**：在 launchd 下用真实模型跑通一轮；备份能恢复。（「第二个守护进程会被拒绝」已在 D3 完成。）

### P2 — 审批闸与账本可上线（Approval gates + Audit log）

- 把提案扩展成 typed 动作集合（发邮件、回复邀约、创建日程……），加上过期和撤回；D1 的 `proposal-<id>` 幂等键沿用到每种动作。
- 给信道加认证（复用 `httpapi.TokenAuth`）。
- 策略即代码：用户批准的「自动批准规则」，例如「回复经理的确认类邮件」。Guardian 只能作为第二审批人，不能扩大权限。
- 借鉴 `dsh-superagent` 的接受模式：每条自动批准规则先在 observe 模式下运行，只在账本里记「本来会自动批准」，用户看过再切到 auto。自动批准的提案记下命中的规则和规则版本；规则变更或停用后，还没发出的提案重新校验，不再满足的退回人工审批。
- 账本按天汇总「你不在时发生了什么」，并支持导出。
- 验收：审批挂起期间重启，事后仍能批准；所有效果都能追到批准人或命中的策略。

### P3 — 真实 MCP 集成，先读后写（Integrations；原 P4，提前）

- 用真实的邮件和日历 MCP server 替换 `mock-mcp`。守护进程只依赖 D1 定下的工具契约（7 个必需工具和它们的参数、结果形状）。不符合契约的 server 先套一层薄适配器，不改守护进程。
- 第一步只开读和轮询，`mail_send` 和 `calendar_respond` 指向仍然模拟的发件端。读通以后再开真实发送，并要求真实 server 支持幂等键，或者由适配器按 `proposal-<id>` 去重。
- **传输**：本机可以优先用 stdio server；需要远端 server 时，再给 `go/mcp` 加 HTTP 传输和 OAuth。凭据只按引用使用，绝不进入模型上下文。

## 6. 横切不变量

- **外部内容一律不可信**：邮件、邀约等触发器发起的回合是 untrusted；只有用户在信道里亲自说的话才是 explicit-human：本机网页上打的字，或远程信道核对过本人账号的消息。
- **远程信道不批准**：远程信道只聊天、回答提问、同步助理的话；批准和拒绝只在本机网页上做。密钥只从环境变量读，不进 plist，不给 MCP 子进程。
- **Worker 没有发送能力**：任何对外效果都只能通过提案加人工决定（或用户批准过的策略）。决定先持久化，再由唯一的发件箱用该提案的幂等键执行；效果工具不进入模型的工具目录。
- **任务不扩大权限**：任务检查是普通的 untrusted 触发器，能做的和其他 worker 回合一样；外部内容驱动的回合只能改自己 thread 上的任务；每个活跃任务总有下一次检查，而且检查次数有上限。
- **单一工具闸门**：所有工具调用都经过 `ToolGate`，账本经由结果观察者记录，不另开第二条执行路径。
- **失败如实上报**：模型调用失败和回合耗尽是失败的回合，不当作回复发到信道。
- **用户的暂停优先**：暂停时不派工、不发信、不跑定时检查，直到用户恢复；自动反馈不会解除暂停。
- **Router 是唯一的信道写入者**：worker 的推理过程和工具调用不外泄到信道；worker 只用 `report` 说明回合的结果，由 router 决定发什么。
- **回答不提权**：用户对提问的回答回到原 thread 时仍按 untrusted 执行，因为那个 thread 的上下文含外部内容。
- **分诊和准备不提权**：推断候选默认只记录，由用户决定是否交给 worker；分诊调用不带工具；后台准备会话只有读工具、按 untrusted 执行，结果回到原 thread，由那里的 worker 决定用户听到什么。
- **看门狗只提醒**：看门狗只记账、发信道、列进「需要你处理」，不取消任务，也不改检查计划。
- **画像只当参考**：用户画像写进 worker 提示时标明不是指令；联系人只从你批准发出的邮件学，不从来信学；记忆整理只删正文重复的条目。
- **检索不改记忆**：检索索引、别名、向量和事实都是派生数据，可以随时重建；Markdown 记忆文件仍是权威；预取的事实和记忆标明只当参考；语义检索默认关，连不上时退回词面检索。
- **事实只听用户和已知联系人**：事实只来自联系人表、已知联系人的来信和会议、你在信道里亲口说的话；陌生人的来信建不了实体，也改不了事实；更弱的来源不替换更强来源的当前值。
- **账本只追加**：每个效果都能追溯到 trigger、session、action_id、批准人。
- **租户互不可见**：fleet 里每个租户只有自己的目录和数据库；令牌只存哈希，未知租户和错误令牌返回同样的 401；管理接口不返回令牌。
- **省钱不丢活**：闸门和额度只推迟工作，不丢弃；睡下之前把下次该醒的时间写进注册表，崩溃时开着的租户立即重新唤醒。
- **默认不变**：`cmd/miniloop` 和 Python 运行时的默认行为不受 demo 影响；新能力一律需显式启用并如实标注状态。

## 7. 明确暂不做

- 远程信道不接群聊、附件、语音和 webhook，也不做浏览器自动化。
- 不做 Router 分片、A2A、端侧 daemon（BYOM）。
- fleet 暂不做多机分片、对象存储复制、自助注册和服务商推送；这些在 D11 的设计里，等真的部署到云上再做。
- 不为 demo 引入 Temporal、PostgreSQL 或向量库；这些都需要先审批依赖。
- 不给 demo 补 Python 对等实现（Go addition 已在 parity matrix 中标注）。
